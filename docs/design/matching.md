# 照合の手がかり

検索語からアプリを見つけるための情報源と、その組み合わせ方。2026-10-27 の検討の記録に、同日に照合の仕様（後半）を足した。数値（点数・しきい値）は評価セット（[testing.md](testing.md#評価セット)）で決める。

## 方針

手作りの辞書は最後の手段にする。先に「汎用の辞書」と「端末の中にすでにある情報」で解き、残りを学習で埋める。

| 手がかり | 得意なもの | 手間 | 状態 |
|---|---|---|---|
| 1. 形態素解析による読み | 表記ゆれ・送り仮名 | 辞書は開発元が管理する | 採用 |
| 1a. ブランド名の読みの表（自前） | 「やふー」→ Yahoo、「ぐーぐる」→ Google | 数百語を作って保守する | 採用（2026-10-27） |
| 2. OS が持つアプリの情報 | ジャンル（地図・メール・電話・カメラ・音楽など）、英語名 | 対応表は数十行 | 採用（ジャンル検索は後回しにしない。2026-10-27） |
| 3. 暗黙の学習 | 残りすべて | なし | 採用（[learning.md](learning.md)） |
| 4. 愛称の辞書（Material Search から流用） | 「アマプラ」などの愛称・略称 | 流用 | 見送り（2026-10-28。評価セットで試すと「のりかえ」で地図のアプリが乗換のアプリより上に出て、送り仮名の全問正解の例が崩れた） |
| 5. Play ストアの情報 | 天気・乗換・金融など、OS の情報に出ないジャンル | 取得の仕組みの保守 | 見送り |
| 6. 端末内の埋め込みモデル | 意味の近さ | 百 MB 規模 | 見送り |

## 1. 形態素解析による読み

- アプリ名を形態素解析器（文を単語に分けて読みを付けるソフト）にかけ、読みをひらがなとローマ字で索引に入れる。検索語も同じ形に正規化して比べる（後述の「照合の仕様」）。
- 採用: Kuromoji 0.9.0 ＋ IPADIC（2026-10-27）。純 Java で Android での実績がある（YomiLauncher）。jar は 13.3 MB。UniDic 版は 46.3 MB で大きすぎる。手元の JVM で、アプリ名らしい 53 語のほとんどに正しい読みが付いた（[reading-sources.md](../research/reading-sources.md)）。
- Android の ICU には日本語の漢字の読みを付ける変換がない（Kvaesitso は Any-Latin を使い、漢字が中国語のピンインになっている）。
- 読みの補いの表（`ReadingSupplements`、2026-10-28 に 5 語）: 辞書の読みは残して候補を足す（通帳→つうちょう、市場→いちば、東日本→ひがしにほん、寿司→ずし、払い→ばらい）。評価セットで外れた語だけを置く。名前と漢字の検索語の両側に使う（T5、2026-11-14）。検索語も語の表記との完全一致で補い、辞書の読みを先に、組み合わせは 8 通りまでにする
- わかっている弱点: 読みは 1 語に 1 つ（「通帳」をかよいちょうと読む、「明日」はあしただけ）。英字の部分には読みが付かない（1a で補う）。固有名詞の誤りは 3 で補う。

### 英字のブランド名の読み

YomiLauncher は英単語の読みの辞書（約 6.7 万語）を持つが、一般の辞書に載らないブランド名は手作業で足している（Google・LINE・PayPay はあり、Yahoo はない）。Mozc の辞書にも、Yahoo・Google などの英字の表記はなかった（[reading-sources.md](../research/reading-sources.md)）。

対策（2026-10-27 に決定）:

1. **ブランド名の読みの表を自前で作る**（`brands.tsv`。綴り→読み。複数の読みを持てる。例: `yahoo` → やふー、`line` → らいん、`x` → えっくす・ついったー）。アプリ名に含まれる英字の語を引いて、読みを検索キーに足す
2. **アプリ名の中の大文字の略語は、1 字ずつの読みも足す**（`NHK` → えぬえいちけー、`UFJ` → ゆーえふじぇー）。表にあるもの（`JAL` → じゃる）は表を優先する。大文字かどうかは**アプリ名の側**で見る。入力は大文字と小文字を区別しない（`nhk` で「NHKプラス」が出る）。この規則は、略語をかなで打つ人（フリック入力で「えぬえいち」など）のためのもので、効果が小さければ評価セットで判断して外す
3. 残りは学習で埋める（[learning.md](learning.md)）

細則（M1-03、2026-10-28）:

- 表は `core/search/src/main/resources/jp/piu/search/core/search/brands.tsv`。列は「綴り・読み・メモ」。書式は `tools:dict` の `checkBrandTable` が `check` で確かめる
- 略語として 1 字ずつ読むのは、NFKC の後が A〜Z と記号だけの語（1 字の大文字を含む。数字・小文字を含む語は除く）。1 字の読みは 1 通り（組み合わせが増えすぎないため）
- 1 字ずつ読むと誤る大文字の語（GO・AWA・OPPO・ATOK・BASE・PAY など）は表に書いて読みを決める
- アプリ名によく出る一般語（maps・pay・plus・on・with など）も表に入れた。短い語は誤って当たる元になりうるので、評価セットで見る
4. 英単語一般の自動変換（e2k の類）は、評価セットで 1〜3 では足りないとわかったときに再検討する

「やふー」で Yahoo 系のアプリがまとめて出る（要件 T2）のは 1 による。「Yahoo!天気」の検索キーが「やふーてんき」になるので、「やふー」の前方一致で Yahoo の名を持つアプリがすべて出る。

### intent filter とカテゴリによるジャンル

ジャンルと「OS への依頼」の対応表を持ち、その依頼を受けられるアプリをジャンルの候補にする。アプリごとの辞書は要らず、新しいアプリも自動で拾える。

| ジャンル | 語（例） | 判定 |
|---|---|---|
| 地図 | ちず・地図・まっぷ・map・なび・ナビ | `ACTION_VIEW` + `geo:0,0?q=`、`CATEGORY_APP_MAPS`、`category=MAPS` |
| メール | めーる・メール・mail | `ACTION_SENDTO` + `mailto:`、`CATEGORY_APP_EMAIL` |
| 電話 | でんわ・電話・tel | `ACTION_DIAL` + `tel:` |
| メッセージ | めっせーじ・SMS | `ACTION_SENDTO` + `smsto:`、`CATEGORY_APP_MESSAGING` |
| カメラ | かめら・カメラ・camera | `MediaStore.ACTION_IMAGE_CAPTURE` |
| 写真 | しゃしん・写真・ぎゃらりー・photo | `ACTION_VIEW` + `image/*`、`CATEGORY_APP_GALLERY`、`category=IMAGE` |
| 動画 | どうが・動画・video | `ACTION_VIEW` + `video/*`、`category=VIDEO` |
| 音楽 | おんがく・音楽・music | `ACTION_VIEW` + `audio/*`、`CATEGORY_APP_MUSIC`、`category=AUDIO` |
| ブラウザ | ぶらうざ・ブラウザ・browser | `ACTION_VIEW` + `https:`、`CATEGORY_APP_BROWSER` |
| カレンダー | かれんだー・予定・calendar | `CATEGORY_APP_CALENDAR`、`ACTION_INSERT` + `CalendarContract.Events` |
| 連絡先 | れんらくさき・連絡先・contacts | `CATEGORY_APP_CONTACTS` |
| 電卓 | でんたく・電卓・計算・calculator | `CATEGORY_APP_CALCULATOR` |
| 時計 | とけい・時計・あらーむ・clock | `AlarmClock.ACTION_SET_ALARM` |
| ファイル | ふぁいる・ファイル・files | `CATEGORY_APP_FILES`（API 29） |
| 天気 | てんき・天気・weather | `CATEGORY_APP_WEATHER`（API 33） |
| 翻訳 | ほんやく・翻訳・translate | `Intent.ACTION_TRANSLATE`（API 29） |
| ストア | すとあ・ストア・store | `CATEGORY_APP_MARKET`、`ACTION_VIEW` + `market://details` |
| PDF | pdf | `ACTION_VIEW` + `application/pdf` |
| ゲーム | げーむ・ゲーム・game | `category=GAME` |
| ニュース | にゅーす・ニュース・news | `category=NEWS` |
| SNS | えすえぬえす・SNS | `category=SOCIAL` |

- ジャンルの付け方（M2-02、2026-10-28）: 依頼を受けた Activity がアプリの入口なら、その入口だけに付ける（電話と連絡先の入口を持つアプリでジャンルが混ざらないように）。入口でない Activity なら、そのアプリの全部の入口に付ける。`category` はアプリ単位なので全部の入口に付ける
- ブラウザの https 問い合わせには `MATCH_ALL` を付ける。既定のブラウザに絞らず、`CATEGORY_APP_BROWSER` を宣言しないブラウザも拾う。カメラは、入口を持つパッケージごとに `setPackage` して `ACTION_IMAGE_CAPTURE` を問い合わせる。暗黙のカメラ問い合わせがシステムアプリだけになる OS でも、後から入れたカメラを拾う。`MATCH_DEFAULT_ONLY` は使わず、`CATEGORY_DEFAULT` のない入口のカテゴリも拾う。
- 仕事用プロファイルのアプリ: `queryIntentActivities` は自分のプロファイルしか見ないので、主プロファイルに同じパッケージがあればその結果を使い、なければ `category` だけで判定する（intent によるジャンルは取れない）
- 型で問う依頼（写真・動画・音楽・PDF）は `content:` の URI を添えて問う。型だけでは `scheme="content"` を書いた filter に当たらない
- ジャンルの id（評価セットと実装で使う。M1-06a で決めた）: `maps email phone messaging camera photos video music browser calendar contacts calculator clock files weather translate store pdf game news social`（表の順）
- ジャンルの語はローマ字の経路でも引ける（`chizu`・`tenki` → 地図・天気のジャンル）
- 「`category=`」は `ApplicationInfo.category`、「`CATEGORY_APP_`」はメイン Activity のカテゴリ。
- `<queries>` は `MAIN`＋`LAUNCHER` だけにする（M2-04）。入口のあるパッケージが見えれば、ジャンルの intent の問い合わせにも出るので、ジャンルごとの宣言は足さない。
- 未確認: 日本のアプリ（Yahoo!マップ・ジョルダンなど）が `geo:` やカテゴリを実際に宣言しているか。実機で `adb shell cmd package query-activities -a android.intent.action.VIEW -d geo:0,0` を試せば確かめられる。実機の試験（M6）の項目に入れる。
- 天気・乗換・銀行のように、OS の情報に出ないジャンルは学習で埋める。

問い合わせの条件の根拠（2026-11-14 確認）: AOSP android14-release の [CrossProfileIntentResolverEngine のブラウザ選択](https://github.com/aosp-mirror/platform_frameworks_base/blob/android14-release/services/core/java/com/android/server/pm/CrossProfileIntentResolverEngine.java#L568)、[ComputerEngine のカメラ判定](https://github.com/aosp-mirror/platform_frameworks_base/blob/android14-release/services/core/java/com/android/server/pm/ComputerEngine.java#L2248) 、[Intent のパッケージ・部品未指定の判定](https://github.com/aosp-mirror/platform_frameworks_base/blob/android14-release/core/java/android/content/Intent.java#L12240) と [MATCH_SYSTEM_ONLY の追加](https://github.com/aosp-mirror/platform_frameworks_base/blob/android14-release/services/core/java/com/android/server/pm/ComputerEngine.java#L2693)。

この変更では索引の版を上げない。ジャンルは毎回判定し、合成の入口も毎回の一覧との比較で削除されるため、既存の索引にも次の同期で反映される。

## 照合の仕様

### 正規化

アプリ名・読み・検索語のすべてに同じ正規化をかける。

1. NFKC（全角・半角や互換文字を統一する Unicode の正規化）
2. 小文字にする（言語に依らない規則で）
3. カタカナをひらがなにする（ヴ → ゔ を含む）
4. 空白・「・」・記号（`!`・`-`・`&`・括弧など）を除く。異体字セレクタ（絵文字の後の U+FE0F、漢字の IVS）と囲み文字（キーキャップ）も除く。除いた結果 NFKC で合成される形になったら、もう一度 NFKC をかける

これを**厳密形**と呼ぶ。加えて、打ち方の揺れを吸収する**緩い形**を作る。

- 長音「ー」を除く（「らーめん」と「らめん」）
- 小さい仮名を普通の仮名にする（「ぁ」→「あ」、「っ」→「つ」、「ゃ」→「や」）
- 「ゔ」を「ぶ」にする

緩い形での一致は、同じ段階の厳密形の一致より下に並べる。

### ローマ字

ローマ字はかなから作る。綴りの流儀の違い（ヘボン式と訓令式など）を吸収するため、**標準形**に揃えてから比べる。

- かな → 標準形: し→`si`、ち→`ti`、つ→`tu`、ふ→`hu`、じ・ぢ→`zi`、しゃ→`sya`、ちゃ→`tya`、じゃ→`zya`、ん→`n`、っ＋子音→子音を重ねる、ー→除く
- 検索語の英字 → 標準形: `shi`→`si`、`chi`→`ti`、`tsu`→`tu`、`fu`→`hu`、`ji`→`zi`、`sha`→`sya`、`cha`→`tya`、`ja`→`zya` など
- 緩い形: 同じ文字の連続を 1 つにし（`nn`→`n`、`kk`→`k`）、`ou`・`oo` → `o`、`uu` → `u`（「とうきょう」の `toukyou` と `tokyo`）

入力の途中（IME の変換前に「のりk」のように英字が残る状態）にも対応するため、検索語は**かなと英字が混ざったまま標準形のローマ字に変換**して、ローマ字の前方一致でも比べる。「のりk」→ `norik` → 「乗換案内」の `norikaeannai` に前方一致する。日本語入力のまま `nhk` と打つと「んhk」になるが、これも `nhk` になる。

ローマ字のキーは、読みからと、英字を残した名前（「NHKプラス」→ `nhk` ＋ `purasu`）の両方から作る。

### カタカナの名前を英字で打つ場合

YomiLauncher では、「ホットペッパーグルメ」が `hot` で出なかった（2026-10-27 のメンテナの試用）。YomiLauncher の検索キーはかなの読みだけで、検索語をそのまま部分一致（SQL の `LIKE '%語%'`）で比べるため、英字の検索語がかなの読みに当たらない（`data/AppIndexDao.kt`・`ui/SearchViewModel.kt` で確認）。

このアプリでは 2 つの経路で出る。

| 検索語 | 経路 | 段階 |
|---|---|---|
| `hot`・`hott`・日本語入力のままの「ほt」 | 読み「ほっとぺっぱーぐるめ」のローマ字 `hottopeppagurume` に前方一致 | 2 |
| `hotpepper`・`hotpe` | パッケージ名 `jp.co.recruit.mtl.android.hotpepper` の語 `hotpepper` に一致 | 2 |
| `pepper` | 同じ語の途中に一致 | 5 |

英語の綴り（`pepper`）とカタカナの読み（`peppa`）は、ローマ字にしても一致しない。パッケージ名に英語の綴りを持つアプリは 2 段目の経路で拾える。どちらにもない場合は学習で埋める。

実装で決めた細則（M1-01、2026-10-27）:

- **入力の途中**: 英字の末尾が綴りの途中なら、どの続きとも共通の部分だけを出す（`sh` → `s`、`ts` → `t`）。`c`・`ch`・`f`・`j` で終わると空になる。照合の側は、空になったローマ字の経路を使わない。かなの末尾（し → しゃ）にはこれをしない（IME は拗音を一度に確定する。入れると「ほて」→ `hot` の誤りが出る）
- **ん**: `nnn` は ん＋な行、`nn` の後が母音か `y` なら ん＋な行（`annai`）、子音か終わりなら ん（`shinnkannsenn` → `sinkansen`）
- **IME の流儀**: `ca`・`cu`・`co` → `k`、`ci`・`ce` → `s`、`cy` → `ty`、`jy` → `zy` を受ける。`xtu`・`ltu`（小さい仮名の打ち方）と旧ヘボン式の `m`（`shimbun`）は受けない
- **外来語の音**: てぃ → `thi`、でぃ → `dhi`（ち・ぢと重ねないため）、ふぁ → `fa`、しぇ → `sye`、を → `wo`
- **促音**: 次の子音を重ねる（「ほっt」→ `hott`）。次が子音でなければ何も出さない
- 漢字・数字はローマ字の出力にそのまま残す（「yahoo天気」→ `yahoo天気`）。アクセント付きのラテン文字は、厳密形では残し、ローマ字の段で外す
- 緩い形に `ei` → `e` は足さない。ローマ字の緩い形は、語の境をまたいで同じ字を 1 つにする（どちらも 2026-10-28 に評価セットで差がなかった）

規則を変えたら、索引の版の番号を上げる（M1-04）。

確かめる例（評価セットに入れる）: `norikae`・`norikaeanai`・`shinkansen`/`sinkansen`・`tokyo`/`toukyou`・`ramen`/`raamen`・`fuji`/`huzi`・`hot`/`hotpepper`/「ほt」→ ホットペッパーグルメ・`nhk`/「んhk」→ NHKプラス。

### 検索キーの生成

アプリ 1 つから、次の検索キーを作る。キーごとに種類を持ち、種類で重みを変える。

| 種類 | 作り方 | 例（Yahoo!天気） |
|---|---|---|
| 名前 | 表示名の厳密形 | `yahoo天気` |
| 読み | 語ごとの読みをつないだもの。かなの語は形態素解析器、英字の語はブランド表と頭字語の規則 | `やふーてんき` |
| ローマ字 | 読みと、英字を残した名前の標準形 | `yahutenki`（`yafu` と打っても標準形は `yahu`）、`yahootenki` |
| 別の言語の名前 | 日本語・英語・端末の言語での表示名（表示名と違うときだけ） | （英語名があれば） |
| パッケージ名 | ありふれた語を除いた残り | `weather` など |
| ジャンル | アプリが属するジャンルの id | `weather`（宣言していれば） |
| 学習 | 学習した検索語（[learning.md](learning.md)） | |

- 英字の部分は形態素解析器の区切りを使わず、空白・記号・字の種類の境で分ける。英字に挟まれたアポストロフィは語の中に入れる（`McDonald's` → `mcdonalds`、`Wi-Fi` → `wi`・`fi`）。連続する英数字がブランド表にある場合は 1 語にして引く（`Qoo10` → きゅーてん）。表にない `LINE2` などは英字と数字を分け、英字の読みを残す。かな・漢字の語は形態素解析器の区切りと読みを使う
- 読みのない語（表にない英字・数字・辞書にない漢字）は、読みのキーの中に表記の厳密形のまま入れる。読みが名前と同じなら名前のキーにまとめる
- 緩い形もキーとして作るときに求めておく（照合の中で変換しない）。語の頭の位置も緩い形に合わせて移す
- 別の言語の名前にも、表示名と同じ規則で読みとローマ字のキーを作る（英語名「Maps」→ `まっぷ`）
- パッケージ名は `.` と `_` で分け、最初の部分（com・jp など）、co・ne・or・ac・android・app・apps・application・mobile・client、1 字の語、数字だけの語を除く
- パッケージ名の語と提供元にも緩い形を保存する。かなの読みからは、索引をメモリに組み立てるときに標準形のローマ字とその緩い形を作り、元の種類・提供元の段・出た理由を保つ（「ぐぐる」「ぐーg」→ パッケージ名や証明書の Google）。英字の綴りそのものはかなのローマ字として解釈し直さない
- ブランド表の読みは「読み」の種類に入れる（「ブランド」という種類は使わない）
- 索引の版の番号は `SearchIndexVersion`。ブランド表の中身のハッシュと版の組をテストで固定し、表を変えたら版を上げるよう促す
- 1 語に読みが複数あるとき（ブランド表で複数の読みを持つ語）は、組み合わせを作る。組み合わせの数に上限を置く（例: 8）
- 語の区切りの位置を覚えておく。「ジョルダン乗換案内」で「あんない」と打ったとき、語の頭からの一致として、語の途中の一致より上に並べるため

### 検索語の扱い

- かな・英字の検索語: 正規化して、厳密形・緩い形・標準形のローマ字を作る
- 漢字を含む検索語（IME で変換を確定した場合）: (1) 名前のキーとの一致をすぐに出し、(2) 形態素解析器で読みを付けて読みのキーと比べた結果を、解析器の準備ができしだい足す。「乗り換え」→ のりかえ → 「乗換案内」。読みの補いも足すので、「通帳」からかなだけの名前「つうちょう」も引ける。検索語の表記と辞書の読みは残す
- 空の検索語: 最近と頻繁に使ったアプリを出す（[ui.md](ui.md)）

### 照合の段階と順位

上の段階ほど先に並べる。ただし、その検索語での学習が十分にあるアプリは、学習の強さに応じた段数だけ上の段階に置き、その段階の先頭に並べる（下の「学習で段階をまたぐ」。2026-11-14）。同じ段階の中は、点（キーの種類の重み＋学習の加点＋起動の加点）の**和**で並べ（2026-10-28 に決めた。よく使うアプリは、当たったキーの種類が違っても同じ段階の中で上に来てよい）、それでも同じなら表示名の順で並べる（結果が毎回同じになるように）。

| 段階 | 条件 | 例 |
|---|---|---|
| 1. 完全一致 | 検索語がキーと等しい | 「ちず」→「地図」アプリ |
| 2. 前方一致 | キーが検索語で始まる | 「のりか」→「乗換案内」 |
| 3. 語の頭からの一致 | キーの語の区切りから検索語で始まる | 「あんない」→「ジョルダン乗換案内」、「まっぷ」→「Yahoo!マップ」 |
| 4. ジャンル | 検索語がジャンルの語に前方一致する（かな 2 字以上、英字 3 字以上） | 「ちず」→ Google マップ・Yahoo!マップ |
| 5. 部分一致 | キーの途中に検索語がある（2 字以上） | 「ぎんこう」→「三井住友銀行」 |
| 6. 頭文字・飛ばし一致 | 英字の検索語（2 字以上）が、英字のキーの文字を順に含む | `gmp` →「Google Maps」 |
| 7. 提供元 | 会社の名前のキー（3 個以上のアプリが持つパッケージ名の語、パッケージ名の語の読み、署名の証明書の組織名）に、完全一致か前方一致（前方一致はかな 2 字・英字 3 字以上） | 「楽天」→ iSPEED（`rakuten_sec`）・iSPEED FX（証明書の `Rakuten Securities, Inc.`）（M6-01） |

- 学習した語（[learning.md](learning.md)）は「学習」の種類のキーとして段階 1〜3 に加わり、回数に応じて加点する。過去にその検索語で選んだアプリにも加点する。
- 学習で段階をまたぐ（learning.md の R6、2026-11-14）: 打った語（か、英字で最後の 1 音を打ちかけた形）で選んだか救済した記録のあるアプリは、「回数 − 1 ＋ 救済なら 1 − 30 日使わなければ 1」段だけ上の段階に置き、その段階で学習のないアプリより先に並べる。元の段階の差が上げる段数以下なら逆転する。「めーる」のメルカリ（段階 2）とメールのアプリ（段階 4）は 3 回の選択で、「ちず」の「地図」（段階 1）とジャンルの Google マップ（段階 4）は 4 回で入れ替わる。差が大きいほど多くの学習を求めるのは、名前の一致という強い手がかりを、押し間違いを含みうる少ない選択で覆さないため。段階の番号の差をそのまま必要な段数にしたのは、規則を 1 つにして説明しやすくするため。印（R4）のある組は上げずに出さない。出た理由は元の当たり方のまま。学習のない検索語の並びは変わらない
- 緩い形・ローマ字の緩い形での一致は、同じ段階の厳密形の一致の直後に並べる。
- 空になった緩い形は、ジャンルの前方一致にも使わない。「ーー」で全ジャンルが出ることを防ぐ。
- 提供元の段は緩い形とローマ字でも完全一致・前方一致だけに限り、前方一致の字数の下限は元の検索語で測る。緩い形のキーで当たった場合は、検索語の形と同じ文字列でも緩い形の一致として並べる。
- 細則（M1-06b、2026-10-28）: パッケージ名の語の完全一致は、厳密形・緩い形のどちらも段階 2 として扱う。~~索引の 3 個以上のアプリが持つパッケージ名の語（google・yahoo など会社の名前）は照合から外す~~（2026-11-06 に改めた。段階 7 に置く）。複合語の区切りは NONE（Kuromoji の NORMAL モード）に決めた。ほかの 2 案は評価セットで差がなかった
- 細則（M1-05、2026-10-28）: かなだけの検索語のローマ字の一致は緩い形として並べる（長音が消え、じ・ぢが重なるため）。段階 6 の 1 字目はキーの頭か語の頭に当て、相手にローマ字のキーを含めない。表示名の順は厳密形の符号位置の順（`Collator` は JDK の版で変わりうる）。名前の「+」は読みとローマ字のキーで「ぷらす」と読む（索引の版 2）。ジャンルの語彙には漢字の語の読み（けいさん・よてい）も入れる
- 起動の加点（仮、`LaunchHistory`）: 回数 1 回につき 3 点（10 回まで）、最後の起動が 1 日以内なら 10 点・7 日以内なら 5 点。段階はまたがない
- 点数は仮の値で `MatchingConfig` に集めてある（種類の重み: 名前 50・別の言語の名前と読み 40・ローマ字 30・学習 30・パッケージ名 20・ジャンル 10）
- 編集距離（打ち間違いの許容）は v1 では入れない。評価セットで必要とわかったら検討する。
- 結果の数に上限を置く（段階 1〜4 と 7 はすべて、5・6 は合わせて 20 件まで）。
- 細則（M6-01、2026-11-06）: パッケージ名から除く語は [research/package-names.md](../research/package-names.md) の 4 分類（ドメインの第 2 レベルは 2 番目の位置のときだけ）。パッケージ名の語のブランド表の読み（yahoo → やふー）は常に段階 7 に置く（名前の段に置くと「まっぷ」で map を持つアプリが Yahoo!マップより上に来たため）。証明書の組織名は、法人の語（inc・ltd・株式会社など）を除いて語に分け、提供元を表さない DN（F-Droid・`O=Android`・`O=Unknown`・Google の `CN=Android, OU=Android, O=Google Inc.` など）は外す。数で外す規則は作らない（1 社で多くのアプリを持つ会社と見分けられないため）。表示名の頭の「Y!」は「やふー」と「わい」の両方で読む。出た理由は「提供元: 〜」

性能の目標: 端末のアプリ 500 個で、入力 1 回あたりの照合が 16 ms（60 Hz の画面の 1 コマ）を十分に下回る。索引はメモリ上にあり、形態素解析は照合の中では行わない。M5-03 から、3,000 個でも測る（`SearchEnginePerformanceTest`）。温めてから検索語（532 個）ごとに 7 回測り、中央値の最も遅いものが 16 ms を下回れば通す（CI の機械で 1 回だけ遅れても落ちないように）。2026-11-03 の JVM の値は、500 個で 0.19 ms、3,000 個で 1.0 ms（索引のヒープは約 4 MB）。

## データモデル

学習した語・ブランド表・愛称の辞書・将来の追加分を、すべて「アプリ（パッケージ名・Activity 名・ユーザー）→ 検索キー → 種類・重み」という同じ形の表に入れる。手がかりを後から足しても照合の部分を変えずに済む。表の定義は [architecture.md](architecture.md#データの保存)。
