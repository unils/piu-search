# 品質とテスト

2026-10-27 の設計。実機で試すのは開発の最後（M6）なので、それまでの品質は自動テストとエミュレータ（PC の上で Android 端末を模すソフト）で確かめる。

## テストの層

| 層 | 何を確かめるか | どこで動くか | 速さ |
|---|---|---|---|
| 1. 単体テスト | 正規化・ローマ字・読み・検索キーの生成・照合・順位・学習の規則 | JVM（`core:*`） | 数秒 |
| 2. 評価セット | 実際のアプリ名と検索語の組で、照合の質を数値で測る | JVM（`core:search`） | 数秒 |
| 3. Robolectric のテスト | 索引の同期・データベース・設定・画面の状態 | JVM（`data`・`app`） | 数十秒 |
| 4. スクリーンショットのテスト | 画面の見た目が意図せず変わっていないか | JVM（`app`） | 数十秒 |
| 5. 計器テスト | 本物の Android での、アプリの一覧・ジャンルの判定・起動・アシスタント・タイル。R8 を通した版（`:release-test`） | エミュレータ | 数分 |
| 6. 性能の計測 | 起動の速さ（`:benchmark`。手で回し、`check` に入れない）・照合の時間（JVM）・メモリ | エミュレータ（実機の値は M6） | 数分 |

- Robolectric: Android の API を JVM の上で模すテストのライブラリ。`PackageManager` に架空のアプリを登録してテストできる
- スクリーンショットのテスト: 画面を画像に描き、保存してある正解の画像と比べる。Roborazzi（Robolectric の上で Compose の画面を描くライブラリ）を使う
- 計器テスト（instrumented test）: エミュレータや実機の上で動くテスト。前後に検査が付く（build-logic の `piu.connected-test-checks`。M5-03）。前は、端末に応答なしの窓（ANR）が出ていれば始めずに落とす。後は、端末ごとに回った数を結果の XML で数え、ソースの `@Test` の数に届かなければ落とす（APK が入らずに 0 件のまま成功になることがあったため）。版で飛ばすテスト（`@SdkSuppress` など）を足すと、古い端末で数が足りずに落ちるので、そのときは数え方を直す

数が多いのは 1 と 2。品質を決める照合と学習を JVM だけで確かめられるように、モジュールを分けた（[architecture.md](architecture.md#モジュール)）。

### テストの道具

- JVM のモジュール: JUnit 6（JUnit Jupiter の API。6.0 は 2025-09 に出た。Java 17 以上が要るが、toolchain の JDK 21 で満たす）。表の形のテストは parameterized test で書く
- Android のモジュール: JUnit 4（Robolectric と計器テストが JUnit 4 を前提にする）
- 正規化の性質のテスト（何度かけても同じ結果になる、など）は、ランダムな文字列を大量に入れて確かめる（property-based test）

## 評価セット

照合の質の物差し。AI が照合を変えるたびに測り、下がっていないことを確かめる。

- `apps.tsv`: 実在するアプリを模した 150 件ほどの一覧（表示名・英語名・パッケージ名・宣言するジャンルの intent）。日本で多く使われるアプリ（交通・金融・買い物・SNS・天気・行政）と、Pixel・GrapheneOS の標準アプリを含める
- `queries.tsv`: 検索語・正解のアプリ（複数可）・分類（表記ゆれ・送り仮名・ローマ字・英字のブランド・頭字語・ジャンル・漢字の検索語・途中まで）
- 指標:
  - 1 位正解率: 正解が 1 位にある割合
  - 3 位以内の正解率
  - MRR（平均逆順位）: 正解の順位の逆数（1 位なら 1、2 位なら 1/2）の平均。順位の細かい上下を拾う
- 分類には、上の 8 つに加えて「学習」（読み・ブランド表・ジャンルでは出せず、学習で埋める想定。旧名・愛称・名前に出ない用途）と「短い語」（go・pay など、正解でないアプリを上に出さないかを見る）がある。「学習」は合格の目安から外して別に数える（M4 で学習の場面として使う）
- 判定は any（正解のどれか 1 つが出ればよい）と all（すべて出る必要がある。「やふー」→ Yahoo 系 9 件など）。all の「3 位以内」の数え方は M1-06b で決める
- 数え方（2026-10-28 に決めた）: any は最も上の正解の順位。all の 3 位以内は「正解がすべて max(3, 正解の数) 位以内」、MRR に使う順位は「最も下の正解の順位 −（正解の数 − 1）」
- 既知の弱点は `queries.tsv` のメモの頭に `既知の弱点: 理由` と書く。**合格の判定でも外れとして数える**（分母から外さない）。全体の 5% まで
- 報告は `core/search/build/reports/eval/`（`eval.md` と `results.tsv`）。前回との差は `-PevalBaseline=<前回の results.tsv>` で出す
- 合格の目安（M1 の終わり）: 3 位以内の正解率 95% 以上。T2（「やふー」で Yahoo 系が全部出る）・送り仮名（「のりかえ」「乗り換え」「乗換」「norikae」）の例は全問正解
- 結果は表にして出し、前回との差（新たに外れた・新たに当たった検索語）を出す。外れたのに直さない検索語は、理由を書いて「既知の弱点」の印を付ける

- 学習の後（M4-01）: 「学習」の分類の検索語ごとに「正解のアプリをすべてのアプリの一覧から 1 回開いた」場面を学習の判定に通し、記録を重ねた索引で全体を測り直す。目安は学習の分類の 3 位以内 90% 以上、ほかの分類が下がらないこと。学習の分類と同じ検索語を教えた語（「ぎんこう」「銀行」）は、ジャンルの分類の正解と同時に満たせない（評価セットの中で求めが矛盾する）ので、「下がらない」の比較から外し、`eval.md` に一覧で出す。M4-01 の時点で 11.6% → 100%

評価セットの検索語は、実機の試験（M6）で困った語を足して育てる。

## Android の部分の確かめ方

- `test-apps:*`: テスト専用の小さなアプリを数個作る。日本語の表示名（「乗換案内テスト」など）、英語の別名、`geo:` の intent filter、`CATEGORY_APP_MAPS` などを持たせる。エミュレータに入れて、索引・ジャンルの判定・起動を確かめる
- テスト用のアプリの一覧は `settings.gradle.kts`、それぞれで確かめることは各アプリの `AndroidManifest.xml` の冒頭の説明にある（M2-01 で 7 つ: 乗換案内テスト・Test Map（既定が英語）・テストメール・将棋テスト（appCategory だけ）・Yahoo!テスト・ランチャーなしテスト・入口二つテスト）
- インストール・更新・削除のあとに、差分の同期（`getChangedPackages`）が効くこと。再起動（`BOOT_COUNT` の変化）のあとに全件を見直すこと
- `QUERY_ALL_PACKAGES` なしで、テスト用のアプリがすべて見えること
- 既定のデジタルアシスタントに設定でき、`ACTION_ASSIST` で検索画面が開くこと
- タイルから開けること（API 34 以上と未満の両方）
- 仕事用プロファイル: エミュレータに仕事用プロファイルを作り（`adb shell pm create-user --profileOf 0 --managed`）、そこのアプリが出て起動できること

エミュレータの版: 最小 SDK の 28、29、33、最新の 37。CI の計器テストは 28 と 37 を手動のときに回す。

### 端末間転送と起動記録の回帰テスト

- `BackupRulesTest` は Android 9〜11 の DB と設定の転送条件、および Android 12 以上の転送領域と全クラウド領域の除外を検査する
- `DeviceTransferTest` は DB を残して `noBackupFilesDir` の印を取り除き、移行先での最初の読み出しを再現する。変更番号・起動回数・更新時刻・仕事用の番号が同じでも索引が全件作り直され、仕事用の学習と起動の記録が返らないことを確かめる。通常の再オープンでは両プロファイルの記録が残ることも確かめる
- 印のない旧版からのスキーマ移行、索引の版の変更と再オープン、中断時の整理の巻き戻しも確かめる。同じインストールでは、別接続の WAL の書き込み中も再オープンして読み出せることを確かめる
- 起動記録の削除は、保存先・メモリの写し・通知・削除後の新しい記録・失敗時の再試行を単体テストで確かめる。設定画面のキャンセル・確定・画面の再作成と、確認窓の日本語・英語のスクリーンショットも対象にする
- 設定のスクリーンショットは、Compose の同じ View を Canvas に描いて撮る。API 37 の PixelCopy が古いフレームを返し、黒い画像になる問題を避けるため（[Robolectric #11392](https://github.com/robolectric/robolectric/issues/11392)、2026-11-13 確認）

## 静的な検査

| 検査 | 道具 |
|---|---|
| 書式 | ktlint（Kotlin の書式の検査）を Spotless（書式の検査と自動修正をまとめる Gradle のプラグイン）から動かす。ソースファイルの先頭のライセンスの見出し（SPDX）も確かめる |
| Android 特有の誤り | Android Lint。警告を残さない（理由のある例外だけ明記して抑える）。`core:*` も `com.android.lint` で対象にする |
| 依存の向き | `core:*` の依存に Android のライブラリが入っていないことを確かめるタスク |
| 依存の版 | 新しい版の有無は Lint では見ない（配布元に問い合わせるので、コードを変えていなくても新しい版が出た日に `check` が落ち、ビルドが再現しない）。Dependabot が更新の pull request を作る |
| 公開 API の説明 | KDoc がない公開 API を検出する。detekt 2（alpha）の `UndocumentedPublic*` の 3 つの規則だけを使う（`config/detekt/detekt.yml`）。安定版の detekt 1.23.8 は Gradle を JDK 25 で動かすと落ち、Dokka は上書きした関数にも KDoc を求めるため。detekt 2 の安定版が出たら上げる |
| 権限 | 出来上がったマニフェストに `INTERNET`・`QUERY_ALL_PACKAGES` がないことを確かめるテスト |
| 依存のライセンス | Licensee（Cash App）で、APK に入る依存のライセンスを SPDX の識別子で判定する。許すライセンスの一覧（`app/build.gradle.kts`）にないものがあれば失敗する。一覧は `app/build/reports/licensee/` に出る。同じ一覧を APK に同梱し（`bundleAndroidAsset`）、アプリのライセンスの画面に、依存の一覧・ライセンスの全文・NOTICE の全文を出す（M5-01。依存を足さない）。MIT・BSD の依存が入るときは、プロジェクトごとの著作権表示が要るので、ライセンスの画面のテストが落ちたら表示の方法を決める |
| 網羅率 | Kover で `core:*` の行の網羅率（テストが通った行の割合）をモジュールごとに測り、80% を下回ったら失敗にする。数値を上げるためのテストは書かない |

## CI

CI（push のたびに自動でビルドとテストを回す仕組み）は GitHub Actions で動かす。

| ジョブ | いつ | 中身 |
|---|---|---|
| check | すべての push と pull request | 書式・Lint・単体テスト・評価セット・Robolectric・スクリーンショット・網羅率・依存とライセンスの検査 |
| instrumented | 手動のときだけ | エミュレータ（API 28・37）で計器テスト（debug と、R8 を通した版の `:release-test`） |
| nightly | 毎日 | API 29・33 の計器テスト、依存の更新の確認 |
| release | 版のタグを付けたとき | 署名つきの APK を作り、GitHub Releases に置く。署名鍵は GitHub の Secrets に置き、リポジトリには入れない |

GitHub Actions の CI には完全にはこだわらない（2026-10-27 のメンテナの判断。課金しておらず、無料の runner ではエミュレータの起動が時間切れになった）。その代わり、**push の前に、手元で CI と同じ形の検査と、エミュレータの計器テストを通す**。エミュレータのジョブは手動のときだけ回す。

Gradle のキャッシュには `gradle/actions/setup-gradle` の `basic`（MIT）を使う。既定の Enhanced Caching は商用の部品のため。外部の Action はコミットの SHA で固定する。

## release の APK の確認

R8（配布用の APK を小さくし、クラスの名前を変える処理）は、資源やリフレクションで探すクラスを取りこぼすことがある。M2-04 では、`BrandTable` の名前が変わって同梱の `brands.tsv` が見つからず、release でだけ索引を作れない不具合を見つけた。計器テスト（debug）では見つからない。

M5-03 から、`:release-test` の計器テスト（`ReleaseApkTest` の 3 件）が下の手順 3〜5 を自動で確かめる。app の `benchmarkRelease`（Baseline Profile のプラグインが release から作る build type。release と同じく R8 を通し、debug の鍵で署名する）を端末に入れ、UiAutomator と shell でアプリの外から操作する。テストのコードは R8 にかけず、アプリのクラスにも触れない。手順 1 の mapping を見ることは、名前が変わると壊れる部品（ブランド表・Kuromoji の辞書・Room の `_Impl`・マニフェストの入口）を使う操作のテストで代えた（`brand-table.pro` の keepnames を外すと落ちることを確かめた）。既存の app の計器テストを R8 の側で回す形は採らなかった（テストのコードも R8 にかかり、アプリの内部に触るのでテストのための keep の規則が要り、Compose のテストの部品を配布物と違う形で入れることになるため）。

手で確かめるときは、次の手順で行う。

1. `./gradlew :app:assembleRelease`。mapping で、名前を残すべきクラス（Kuromoji の `Tokenizer$Builder`・`BrandTable`・Room の `_Impl`）が残っていることを見る
2. 未署名の APK を手元の debug の鍵で `apksigner` で署名し（ビルドの設定には入れない）、エミュレータに `adb install`
3. 開き、logcat（タグ `PiuIndexSync`）で同期の成功を見る。`adb shell input text norikae` などで打ち、`uiautomator dump` で結果を読む
4. `adb shell input keyevent KEYCODE_ASSIST` と、タイル（`cmd statusbar add-tile` → `expand-settings` → `click-tile`）から開け、同じ画面が使い回されることを見る
5. `force-stop` して開き直し、データベースから読めること（同期が差分になる）と、起動の記録が残ること（空の検索語の一覧に出る）を見る

## 起動の速さ（M5-03）

`:benchmark`（Macrobenchmark）で、app の `benchmarkRelease`（R8 を通した版）の起動を測る。冷えた状態（プロセスなし）と温まった状態（プロセスを残し、画面を作り直す）、コンパイルの状態（`None`: 先にコンパイルしない・`BaselineProfile`）の組ごとに 15 回。指標は最初の描画（`timeToInitialDisplayMs`）と、検索窓に焦点が来て打てるまで（`timeToFullDisplayMs`。アプリが `ReportDrawnWhen` で `reportFullyDrawn` を出す）。手順は CONTRIBUTING の「起動の速さと Baseline Profile」。

2026-11-03 のエミュレータの値（中央値、ms。Baseline Profile にアプリの分を加えた後）:

| 端末 | 冷えた・最初の描画 | 冷えた・打てるまで | 温まった・最初の描画 | 温まった・打てるまで |
|---|---|---|---|---|
| API 37 | 275 | 312 | 56 | 77 |
| API 26（当時の測定。現在は対象外） | 391 | 391 | 117 | 117 |

目標の案（温まった状態で 300 ms 以内）は満たす。アプリの分の Baseline Profile を加えた前後の差は、回ごとのばらつき（四分位範囲 10〜60 ms）の中に収まった。効き目は M6 の実機で見る。API 26 で 2 つの指標が同じになるのは、焦点が最初の描画より前に来るためと見ている（未確認）。

### 起動用のプロファイルと DEX の並べ替え

Baseline Profile の生成（`BaselineProfileGenerator`）のうち、呼び出してから検索窓に焦点が来るまでの流れ（`startup`）を `includeInStartupProfile = true` で集め、起動用のプロファイル（`startup-prof.txt`）にも入れる。R8 はこれに載ったクラスを最初の DEX（`classes.dex`）にまとめる（DEX の並べ替え。app の `baselineProfile { dexLayoutOptimization = true }`）。起動のときに読む DEX の頁が減るので、公式の文書は Baseline Profile だけのときより起動が 15〜30% 速いことが多いとしている。

- 入口（アイコン・アシスタント・タイル）はどれも `SearchActivity` を開き、そこからの流れは同じなので、アイコンからの起動だけを通す。検索語を打った後の照合は入れない（公式の文書は、起動用の流れを `classes.dex` に収まる範囲に絞るよう勧める）
- 起動の流れには、画面の表示の後に裏のスレッドで辞書を読み込む Kuromoji（`warmUp`）の分も入る。それでも起動用のクラスは `classes.dex` に収まった
- release の APK は、`classes.dex`（起動用。1.66 MB）と `classes2.dex`（残り。0.97 MB）の 2 つに分かれた。以前は `classes.dex` 1 つ（2.42 MB）。AAB の R8 の記録（`BUNDLE-METADATA/com.android.tools/r8.json`）で、`classes.dex` が `"startup": true` になることを確かめた

2026-11-08 のエミュレータの値（中央値と四分位範囲、ms。前は Baseline Profile だけ、後は起動用のプロファイルと DEX の並べ替えを加えたもの。コンパイルの状態は `BaselineProfile`）:

| 端末 | 状態 | 指標 | 前 | 後 |
|---|---|---|---|---|
| API 37 | 冷えた | 最初の描画 | 270（263〜274） | 267（261〜274） |
| API 37 | 冷えた | 打てるまで | 303（296〜310） | 303（299〜319） |
| API 37 | 温まった | 最初の描画 | 56（53〜61） | 55（53〜63） |
| API 37 | 温まった | 打てるまで | 75（72〜83） | 74（72〜83） |
| API 26（当時の測定。現在は対象外） | 冷えた | 打てるまで | 406（393〜467） | 416（394〜445） |
| API 26（当時の測定。現在は対象外） | 温まった | 打てるまで | 119（106〜129） | 112（92〜115） |

API 26 は 2 つの指標が同じ値なので、打てるまでだけを載せた。前後の差はどれも四分位範囲の中で、エミュレータでは効き目が見えなかった。エミュレータの DEX は手元のディスクのファイルのキャッシュに載っていて、頁を読む時間がほとんどかからないためと見ている（未確認）。効き目は実機で見る。

## 公開前の検査（M7）

- 再現可能なビルド: 同じソースから 2 回ビルドして、APK が同じになること（F-Droid の推奨）。APK の Baseline Profile（`assets/dexopt/baseline.prof`）と、起動用のプロファイルで並べ替えた DEX も含めて確かめる。プロファイルの元（`app/src/release/generated/baselineProfiles/` の `baseline-prof.txt` と `startup-prof.txt`）はリポジトリに入れてあり、ビルドのたびには生成しない
- 端末の言語を英語・中国語にしても壊れないこと
- ライセンスの表示（Kuromoji の Apache-2.0、IPADIC のライセンス、流用した辞書）がアプリ内と NOTICE にあること
