# 品質とテスト

2026-10-27 の設計（保存・同期・画面の回帰テストと測定値は 2026-11-14 更新）。Android に依存しない処理は JVM で、OS との連携はエミュレータと実機で確かめる。

## テストの層

| 層 | 何を確かめるか | どこで動くか | 速さ |
|---|---|---|---|
| 1. 単体テスト | 正規化・ローマ字・読み・検索キーの生成・照合・順位・学習の規則 | JVM（`core:*`） | 数秒 |
| 2. 評価セット | 実際のアプリ名と検索語の組で、照合の質を数値で測る | JVM（`core:search`） | 数秒 |
| 3. Robolectric のテスト | 索引の同期・データベース・設定・画面の状態 | JVM（`data`・`app`） | 数十秒 |
| 4. スクリーンショットのテスト | 画面の見た目が意図せず変わっていないか | JVM（`app`） | 数十秒 |
| 5. 計器テスト | 本物の Android での、アプリの一覧・ジャンルの判定・起動・アシスタント・タイル。R8 を通した版（`:release-test`） | エミュレータ | 数分 |
| 6. 性能の計測 | 起動の速さ（`:benchmark`。手で回し、`check` に入れない）・照合の時間（JVM）・メモリ | エミュレータ（実機の値は測ったときに記す） | 数分 |

- Robolectric: Android の API を JVM の上で模すテストのライブラリ。`PackageManager` に架空のアプリを登録してテストできる
- スクリーンショットのテスト: 画面を画像に描き、保存してある正解の画像と比べる。Roborazzi（Robolectric の上で Compose の画面を描くライブラリ）を使う
- 計器テスト（instrumented test）: エミュレータや実機の上で動くテスト。前後に検査が付く（build-logic の `piu.connected-test-checks`。M5-03）。前は、端末に応答なしの窓（ANR）が出ていれば始めずに落とす。後は、端末ごとに回った数を結果の XML で数え、ソースの `@Test` の数に届かなければ落とす（APK が入らずに 0 件のまま成功になることがあったため）。版で飛ばすテスト（`@SdkSuppress` など）を足すと、古い端末で数が足りずに落ちるので、そのときは数え方を直す

数が多いのは 1 と 2。品質を決める照合と学習を JVM だけで確かめられるように、モジュールを分けた（[architecture.md](architecture.md#モジュール)）。

### テストの道具

- JVM のモジュール: JUnit 6（JUnit Jupiter の API。6.0 は 2025-09 に出た。Java 17 以上が要るが、toolchain の JDK 21 で満たす）。表の形のテストは parameterized test で書く
- Android のモジュール: JUnit 4（Robolectric と計器テストが JUnit 4 を前提にする）
- 正規化の性質のテスト（何度かけても同じ結果になる、など）は、ランダムな文字列を大量に入れて確かめる（property-based test）

## 評価セット

照合の質の物差し。AI が照合を変えるたびに測り、下がっていないことを確かめる。

- `apps.tsv`: 実在するアプリを模した 150 件ほどの一覧（表示名・英語名・パッケージ名・宣言するジャンルの intent）。日本で多く使われるアプリ（交通・金融・買い物・SNS・天気・行政）と、Pixel・GrapheneOS の標準アプリを含める
- `queries.tsv`: 検索語・正解のアプリ（複数可）・分類（表記ゆれ・送り仮名・ローマ字・英字のブランド・頭字語・ジャンル・漢字の検索語・途中まで）
- 指標:
  - 1 位正解率: 正解が 1 位にある割合
  - 3 位以内の正解率
  - MRR（平均逆順位）: 正解の順位の逆数（1 位なら 1、2 位なら 1/2）の平均。順位の細かい上下を拾う
- 分類には、上の 8 つに加えて「学習」（読み・ブランド表・ジャンルでは出せず、学習で埋める想定。旧名・愛称・名前に出ない用途）と「短い語」（go・pay など、正解でないアプリを上に出さないかを見る）がある。「学習」は合格の目安から外して別に数える（M4 で学習の場面として使う）
- 判定は any（正解のどれか 1 つが出ればよい）と all（すべて出る必要がある。「やふー」→ Yahoo 系 9 件など）。all の「3 位以内」の数え方は M1-06b で決める
- 数え方（2026-10-28 に決めた）: any は最も上の正解の順位。all の 3 位以内は「正解がすべて max(3, 正解の数) 位以内」、MRR に使う順位は「最も下の正解の順位 −（正解の数 − 1）」
- 既知の弱点は `queries.tsv` のメモの頭に `既知の弱点: 理由` と書く。**合格の判定でも外れとして数える**（分母から外さない）。全体の 5% まで
- 報告は `core/search/build/reports/eval/`（`eval.md` と `results.tsv`・`results-learned.tsv`）
- 合格の目安（M1 の終わり）: 3 位以内の正解率 95% 以上。T2（「やふー」で Yahoo 系が全部出る）・送り仮名（「のりかえ」「乗り換え」「乗換」「norikae」）の例は全問正解
- 結果は表にして出す。外れたのに直さない検索語は、理由を書いて「既知の弱点」の印を付ける
- 基準（2026-11-14 から）: 今の結果を `eval/baseline.tsv` にコミットし、検索語ごとの順位（指標に使う順位と 3 位以内か。学習のない状態と学習の後の両方）を比べる。1 件でも下がるか、評価セットと行が食い違えば check が落ち、失敗の文に下がった検索語と順位を書く。上がった語は落とさず、`eval.md` の「基準との差」に出す。評価は決定的なので、率の許し幅は設けない。分類ごとの率で比べると、ある語が上がって別の語が下がったときに見逃すので、検索語ごとに比べる
- 照合や評価セットを意図して変えたら、`./gradlew :core:search:updateEvalBaseline` で基準を書き直し、`baseline.tsv` の差分（順位の変わった行）を pull request で見せる。上位のアプリの名前は基準に入れず、差分を順位の変わった行だけにする

- 学習の後（M4-01）: 「学習」の分類の検索語ごとに「正解のアプリをすべてのアプリの一覧から 1 回開いた」場面を学習の判定に通し（正解が学習のない状態で上位 5 件に見えていれば、検索の結果から 3 回選んだ場面にする。2026-11-14、R6。見えているアプリを一覧から開いても学習にならず、選び続けた状態で段階をまたぐかを見るため。「めーる」の行）、記録を重ねた索引で全体を測り直す。目安は学習の分類の 3 位以内 90% 以上、ほかの分類が下がらないこと。学習の分類で教えた語そのものを打った行（「ぎんこう」を「銀行」「ginkou」と打つ形と、最後の 1 音までの打ちかけ「ginko」「ぎんk」）は、ジャンルの分類の正解と同時に満たせない（評価セットの中で求めが矛盾する）ので、「下がらない」の比較から外し、`eval.md` に一覧で出す。教えた語の頭にあたる別の語（「しんかんせんよやく」に対する「shinkansen」）は、学習の副作用を見るために比べる。M4-01 の時点で 11.6% → 100%

評価セットの検索語は、実機で困った語を足して育てる。

### 照合の細部の回帰テスト（T5）

`MatchingDetailsTest` は Qoo10 の表示名の読み（全角・半角、解析器あり・なし）、パッケージ名と証明書の読みの緩い形・ローマ字、段階 7 の完全一致と前方一致の字数の下限、部分一致と飛ばし一致の除外、厳密形を先にする順位、長音だけの検索語、パッケージ名の緩い形の完全一致を段階 2 に下げる規則を検査する。表にない英数字の区切りと空白の区切りも残す。提供元のローマ字は、短くても完結した完全一致なら認め、入力途中の `sh` → `s` を完全一致に使わないことも確かめる。

読みの補いを検索語側にも使う判断には、`eval/reading-supplements.tsv` と `ReadingSupplementsEvalTest` を使う。かなだけの架空の表示名を使い、漢字の表記一致による成功を除く。通帳・市場の補い、複数の語の組み合わせ、辞書の読みの保持、英字の混在を 7 行で測る。語の表記が完全一致したときだけ補い、候補が 8 通りで止まること、漢字の表記・辞書の読み・補いの読みで同時に引け、出た理由を区別できることも単体テストで検査する。報告は `build/reports/eval/reading-supplements.md`。

2026-11-14 の JVM 単体テストによる比較:

| 評価の対象 | 前 | 後 |
|---|---:|---:|
| 既存 463 行（学習を除く）の 1 位正解率 | 95.7% | 95.7% |
| 同 3 位以内の正解率 | 96.8% | 96.8% |
| 同 MRR | 0.972 | 0.972 |
| 読みの補いの追加評価 7 行の 3 位以内の正解率 | 28.6%（2/7） | 100.0%（7/7） |

既存の検索語 532 行は、学習前・学習後とも評価に使う順位が変わらなかった。追加評価の改善と既存評価の維持を根拠に、検索語側の読みの補いを採用した。追加評価は限定した架空の名前による再現例であり、未知の名前での精度を示す値ではない。

## Android の部分の確かめ方

- `test-apps:*`: テスト専用の小さなアプリを数個作る。日本語の表示名（「乗換案内テスト」など）、英語の別名、`geo:` の intent filter、`CATEGORY_APP_MAPS` などを持たせる。エミュレータに入れて、索引・ジャンルの判定・起動を確かめる
- テスト用のアプリの一覧は `settings.gradle.kts`、それぞれで確かめることは各アプリの `AndroidManifest.xml` の冒頭の説明にある（M2-01 の 7 つ: 乗換案内テスト・Test Map（既定が英語）・テストメール・将棋テスト（appCategory だけ）・Yahoo!テスト・ランチャーなしテスト・入口二つテスト。T7 でブラウザ 2 つとカメラを追加）
- インストール・更新・削除のあとの同期で、写しに反映されること（`IndexActorInstrumentedTest`）
- 端末のすべての入口（テスト用のアプリに限らない）で、同じ状態のまま同期を続けると何も読み直さず、失敗もないこと（`IndexActorInstrumentedTest`。残った再試行と欠けを assert の文に出す）。エミュレータには時刻 0 の入口も仕事用プロファイルもないので、時刻 0 の APK での収束は実機の確認（[release.md](../release.md)）と単体テストで見る
- `QUERY_ALL_PACKAGES` なしで、テスト用のアプリがすべて見えること
- 既定のデジタルアシスタントに設定でき、`ACTION_ASSIST` で検索画面が開くこと
- タイルから開けること（API 34 以上と未満の両方）
- 仕事用プロファイル: エミュレータに仕事用プロファイルを作り（`adb shell pm create-user --profileOf 0 --managed`）、そこのアプリが出て起動できること

エミュレータの版: 最小 SDK の 28、29、33、最新の 37。CI の計器テストは 28 と 37 を手動のときに回す。

### ジャンルと入口・索引の版の回帰テスト（T7）

- `GenreResolverTest` は AOSP の制限を模した PackageManager を使い、既定を切り替えても両ブラウザが残ること、後から入れたカメラを拾うこと、同じパッケージの複数入口・プロファイルでカメラの問い合わせを重ねないことを API 28・37 で確かめる
- `AppSourceTest` は合成の `android.app.AppDetailsActivity` を混ぜ、全件・パッケージ指定・差分用の一覧・詳細のどれにも入らないことを API 28・37 で確かめる。同じ末尾の通常の Activity は残す
- 生成器の版（索引の版）の変更は、`IndexRulesTest` が確かめる（欠けのない組はキーだけを作り直し、欠けのある組は材料から作り直す）。読めないプロファイルの組は前の写しのまま残り、読めるようになった同期で作り直される
- `test-apps:browser`・`browser-secondary` は `APP_BROWSER` なしで http/https を受ける。`camera` は権限なしで `IMAGE_CAPTURE` を受ける。名前はジャンル語を含めず、通常のユーザーアプリとして入れる
- `GenreResolverInstrumentedTest` は両ブラウザとカメラのジャンルを本物の OS で確かめる。API 31 以上では既定ブラウザを順番に替えて両方が残ることを確かめ、最後に元の設定へ戻す。それより古い OS では設定を替えずに判定する。`InstalledAppReaderInstrumentedTest` と app の導入確認にも 3 アプリを含める

`GenreResolverInstrumentedTest` は計器テスト（`connectedDebugAndroidTest`）に含まれ、API 28 と 37 のエミュレータで回す。カメラのパッケージ別の問い合わせの時間は、上の Robolectric の計測（`GenreResolverTest`）だけで、端末では測っていない。

### 端末間転送と起動記録の回帰テスト

- `BackupRulesTest` は Android 9〜11 の DB と設定の転送条件、および Android 12 以上の転送領域と全クラウド領域の除外を検査する
- `RecordsInstallationGuardTest` は、新規のインストール・0.2.0 からの同じ端末の更新（0.2.0 の印のファイルの名前と書式を固定）・転送（印を取り除き、自分の番号の記録だけが残ること）・自分の番号が 0 でない場合を確かめる。整理と印の更新の途中の失敗が巻き戻り、次の読み込みで再試行されること。空・途中まで・読み取り不能の印からの復旧（API 28・37）と、復旧後の印が保存されて新しい仕事用の記録が再オープンで消えないこと。印を保存できない間は、開くたびに整理すること。印が一致する照合は、別の接続の WAL の書き込み中も待たないこと
- 索引は転送しないので（`index.db` は転送の規則から外す）、転送の後は空から作り直す。印のない旧版からの移行は `RecordsMigrationTest` が確かめる
- 起動記録の削除は、保存先・メモリの写し・通知・削除後の新しい記録・失敗時の再試行を単体テストで確かめる。設定画面のキャンセル・確定・画面の再作成と、確認窓の日本語・英語のスクリーンショットも対象にする
- 設定のスクリーンショットは、Compose の同じ View を Canvas に描いて撮る。API 37 の PixelCopy が古いフレームを返し、黒い画像になる問題を避けるため（[Robolectric #11392](https://github.com/robolectric/robolectric/issues/11392)、2026-11-13 確認）

### 保存・起動・プロファイルの回帰テスト（R1〜R3）

記録の規則（失敗の間に書かない・取り消しの無効化・全消去・削除したプロファイルへの遅い書き込みの拒否・整理の再試行）は、`core:state` の `RecordsRulesTest`・`RecordsLawsTest` と、data の `RecordsActorTest`（本物の Room とトリガーによる故障）が確かめる。app は、画面と書き手のつなぎ方を確かめる。

| テスト | 確かめること |
|---|---|
| `SearchViewModelTest` | 偽の書き手と仮想の時計で、保存の完了前に起動しないこと、保存の失敗でも起動し次の画面で控えめに知らせること、一時停止中の仕事用への要求を記録しないこと、呼び直し・回転・連打・起動の失敗の扱い、使った学習の組を判断に入れること、知らせの表示・取り消し・消費、前面への復帰での読み直しと忘却 |
| `OpenFlowTest`（Robolectric、API 28・37） | 本物の画面と `piu.db` で、学習と起動の記録を OS に頼む前に同じトランザクションで書くこと、保存の失敗ではどちらの記録も書かれないこと、保存中の回転・起動中の停止・閉じかけの画面への追加のタップ |
| `LearnedListFailureTest` | 削除・全消去・ファイルから合わせた学習の保存の失敗を表示し、写しを変えないこと |
| `LearningTransferTest` | 書き出し・読み込みの失敗と、捨てた件数の数え方。ログに URI と例外のメッセージを出さないこと |
| `AppStartupTest` | 0.2.0 の版 6 の `piu.db` から製品の組み立てのまま起動し、記録が残り、索引の表が落ち、消えたプロファイルの記録が検索画面を開かずに整理されること |
| `AppLauncherTest` | 一時停止の判定は準備の時点、起動先は OS に渡す直前に引き直すこと |
| `ProfileWatcherTest`・`ExistingProfilesTest` | 放送で読み直すこと、問い合わせの失敗で前の値を保つこと。一時停止や問い合わせ失敗を削除にしないこと |

回転とセッションの詳しい条件は[後述](#画面の状態と派生の索引r5)する。

### 索引の同期

索引の同期（[architecture.md](architecture.md#索引の作成と更新)）は、規則・書き手・読み手・保存の層に分けて、端末なしで確かめる。

| テスト | 確かめること |
|---|---|
| `IndexLawsTest`（`core:state`） | 乱数の端末の変化と失敗の列で、法則 1〜5 が成り立つこと。収束（再試行の枠がなく新しい知らせもなければ、同じ端末の 2 回目は材料もキーも読まない）・一覧の入口は必ず索引に入る・読めないプロファイルの組は前の写しのまま・鍵は成否によらず今の値・回復（読めるようになればその回にキーも作り直され、安定すれば全件を作り直した結果と一致する） |

## CI

CI（push のたびに自動でビルドとテストを回す仕組み）は GitHub Actions で動かす。

| ジョブ | いつ | 中身 |
|---|---|---|
| check | すべての push と pull request | 書式・Lint・単体テスト・評価セット・Robolectric・スクリーンショット・網羅率・依存とライセンスの検査。debug と release の APK と計器テストの APK も組み立てる |
| instrumented | 手動のときだけ | エミュレータ（API 28・37）で計器テスト（debug と、R8 を通した版の `:release-test`） |

配布の APK は CI では作らない。メンテナが手元で組み立てて自分の鍵で署名し、GitHub Releases に置く（[release.md](../release.md)）。署名鍵を CI に預けないため。依存の更新の確認は Dependabot が行う。

GitHub Actions の CI には完全にはこだわらない（2026-10-27 のメンテナの判断。課金しておらず、無料の runner ではエミュレータの起動が時間切れになった）。その代わり、**push の前に、手元で CI と同じ形の検査と、エミュレータの計器テストを通す**。エミュレータのジョブは手動のときだけ回す。

Gradle のキャッシュには `gradle/actions/setup-gradle` の `basic`（MIT）を使う。既定の Enhanced Caching は商用の部品のため。外部の Action はコミットの SHA で固定する。

## release の APK の確認

R8（配布用の APK を小さくし、クラスの名前を変える処理）は、資源やリフレクションで探すクラスを取りこぼすことがある。M2-04 では、`BrandTable` の名前が変わって同梱の `brands.tsv` が見つからず、release でだけ索引を作れない不具合を見つけた。計器テスト（debug）では見つからない。

M5-03 から、`:release-test` の計器テスト（`ReleaseApkTest` の 3 件）が下の手順 3〜5 を自動で確かめる。app の `benchmarkRelease`（Baseline Profile のプラグインが release から作る build type。release と同じく R8 を通し、debug の鍵で署名する）を端末に入れ、UiAutomator と shell でアプリの外から操作する。テストのコードは R8 にかけず、アプリのクラスにも触れない。手順 1 の mapping を見ることは、名前が変わると壊れる部品（ブランド表・Kuromoji の辞書・Room の `_Impl`・マニフェストの入口）を使う操作のテストで代えた（`brand-table.pro` の keepnames を外すと落ちることを確かめた）。既存の app の計器テストを R8 の側で回す形は採らなかった（テストのコードも R8 にかかり、アプリの内部に触るのでテストのための keep の規則が要り、Compose のテストの部品を配布物と違う形で入れることになるため）。

手で確かめるときは、次の手順で行う。

1. `./gradlew :app:assembleRelease`。mapping で、名前を残すべきクラス（Kuromoji の `Tokenizer$Builder`・`BrandTable`・Room の `_Impl`）が残っていることを見る
2. 未署名の APK を手元の debug の鍵で `apksigner` で署名し（ビルドの設定には入れない）、エミュレータに `adb install`
3. 開き、logcat（タグ `PiuIndexSync`）で同期の成功を見る。`adb shell input text norikae` などで打ち、`uiautomator dump` で結果を読む
4. `adb shell input keyevent KEYCODE_ASSIST` と、タイル（`cmd statusbar add-tile` → `expand-settings` → `click-tile`）から開け、同じ画面が使い回されることを見る
5. `force-stop` して開き直し、データベースから読めること（材料を読み直さない）と、起動の記録が残ること（空の検索語の一覧に出る）を見る

## 起動の速さ（M5-03）

`:benchmark`（Macrobenchmark）で、app の `benchmarkRelease`（R8 を通した版）の起動を測る。冷えた状態（プロセスなし）と温まった状態（プロセスを残し、画面を作り直す）、コンパイルの状態（`None`: 先にコンパイルしない・`BaselineProfile`）の組ごとに 15 回。指標は最初の描画（`timeToInitialDisplayMs`）と、検索窓に焦点が来て打てるまで（`timeToFullDisplayMs`。アプリが `ReportDrawnWhen` で `reportFullyDrawn` を出す）。手順は [developer-guide.md](../developer-guide.md#起動時間の計測と-baseline-profile)。

2026-11-03 のエミュレータの値（中央値、ms。Baseline Profile にアプリの分を加えた後）:

| 端末 | 冷えた・最初の描画 | 冷えた・打てるまで | 温まった・最初の描画 | 温まった・打てるまで |
|---|---|---|---|---|
| API 37 | 275 | 312 | 56 | 77 |
| API 26（当時の測定。現在は対象外） | 391 | 391 | 117 | 117 |

### 起動用のプロファイルと DEX の並べ替え

Baseline Profile の生成（`BaselineProfileGenerator`）のうち、呼び出してから検索窓に焦点が来るまでの流れ（`startup`）を `includeInStartupProfile = true` で集め、起動用のプロファイル（`startup-prof.txt`）にも入れる。R8 はこれに載ったクラスを最初の DEX（`classes.dex`）にまとめる（DEX の並べ替え。app の `baselineProfile { dexLayoutOptimization = true }`）。起動のときに読む DEX の頁が減るので、公式の文書は Baseline Profile だけのときより起動が 15〜30% 速いことが多いとしている。

- 入口（アイコン・アシスタント・タイル）はどれも `SearchActivity` を開き、そこからの流れは同じなので、アイコンからの起動だけを通す。検索語を打った後の照合は入れない（公式の文書は、起動用の流れを `classes.dex` に収まる範囲に絞るよう勧める）
- 起動の流れには、画面の表示の後に裏のスレッドで辞書を読み込む Kuromoji（`warmUp`）の分も入る。それでも起動の経路の主なクラス（app と data）は `classes.dex` に入った（Compose の一部など、`classes2.dex` に残る起動用のクラスもある）
- 同じく裏で進む、記録と索引の読み込み（記録の書き手 `RecordsActor`・索引の書き手 `IndexActor`・`ProfileWatcher`・`core/state` の規則・保存した索引の復元）も起動の流れに入る。検索の流れ（`search`）は、結果の行を押して開くところまで通し、記録の保存から OS への起動の要求までを Baseline Profile に採る（1 回しか通らないので hot の印は付かない）
- release の APK は、`classes.dex`（起動用）と `classes2.dex`（残り）の 2 つに分かれる（2026-11-23 の v0.3 で 1.75 MB と 1.01 MB。分ける前は `classes.dex` 1 つ）。AAB の R8 の記録（`BUNDLE-METADATA/com.android.tools/r8.json`）で、`classes.dex` が `"startup": true` になることを確かめた

2026-11-08 のエミュレータの値（中央値と四分位範囲、ms。前は Baseline Profile だけ、後は起動用のプロファイルと DEX の並べ替えを加えたもの。コンパイルの状態は `BaselineProfile`）:

## 公開前の検査（M7）

- 再現可能なビルド: 同じソースから 2 回ビルドして、署名なしの APK がバイト単位で同じになること（F-Droid が比べるため）。`tools/reproducible-build/check.sh` が、別の 2 つのディレクトリで順に組み立てて比べる（手順は [release.md](../release.md)）。APK の Baseline Profile（`assets/dexopt/baseline.prof`・`baseline.profm`）と、起動用のプロファイルで並べ替えた DEX も比べる対象に入る。プロファイルの元（`app/src/release/generated/baselineProfiles/` の `baseline-prof.txt` と `startup-prof.txt`）はリポジトリに入れてあり、ビルドのたびには生成しない。2026-11-15 に 0.1.0 の候補のコミットで、`--max-workers` を 4 と 4、4 と 1 にして 2 回ずつ組み立て、4 つの APK がすべて一致した。同じ PC と同じ JDK での結果で、F-Droid の組み立て（Debian の OpenJDK 21）との一致は申請のときに `fdroid build` で確かめる
- 端末の言語を英語・中国語にしても壊れないこと
- ライセンスの表示（Kuromoji の Apache-2.0、IPADIC のライセンス、流用した辞書）がアプリ内と NOTICE にあること

## 画面の状態と派生の索引（R5）

`SearchViewModelTest` は、読みと派生の索引の裏の仕事を手動の Dispatcher に溜めて、順序を確かめる。未開始の読みを最新の 1 件にまとめて解析前に捨てること、解析中の追加要求と古い結果の破棄、閉じた後の生成完了で入力の記録と解析を再開しないこと、起動の記録だけ・同じ学習の中身・同じ写しの再送では派生の索引を作り直さないこと、古い入力の完成を採らないこと、派生の処理を止めたままでも、消えた仕事用や「出さない」にした仕事用のアプリを出さず開かないこと、索引の書き手の状態だけの変化（同期の失敗と回復）で知らせだけが変わること。

`SavedSearchStateTest`（Robolectric、API 28・37）は、本物の画面の作り直しで、構成の変更では同じ ViewModel と検索語・全アプリの表示を保ち、プロセスの作り直しでは検索語だけを戻すことを確かめる。`RecreationTest` は、本物の記録の書き手を止めて、保存中に回転→保存完了→7 秒経過→画面を閉じて検索を開き直す、で知らせを取り消せること、画面を閉じたら出しかけの知らせを消費すること、ファイル操作の結果を回転後も表示できることを確かめる。
